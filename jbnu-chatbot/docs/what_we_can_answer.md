> # ★ 13% 는 "우리가 아는 게 13%" 지 "학생이 받는 게 나빠졌다" 가 아니다
>
> **배포 조건은 안 움직였다.** `확신하고 틀린 것 0건` 그대로다.
> 학생이 받는 답은 8/17 과 8/18 이 **똑같다** — 바뀐 것은 자뿐이다.
>
> ```
> 85%  →  37%   자를 고쳤다 (인용문에서 찾나 · 경로에서 찾나)
> 38%  →  13%   자를 고쳤다 (문서를 찾았나 · 맞는 문서인가)
> ```
>
> 두 번 다 **숫자가 내려간 게 아니라 원래 그 상태였다.**
> 34건은 답을 냈지만 그게 맞는 문서인지 사람이 확인한 적이 없다.
> 확인 안 한 걸 통과로 세는 것이 거짓말이고, 그 거짓말을 없앤 숫자가 13% 다.
>
> ★ 집행부에 보일 때 이 문장이 같이 가야 한다. 안 그러면
>   "챗봇이 나빠졌다" 로 읽힌다. 나빠진 건 없다 — 보이게 됐을 뿐이다.

# ② 표 렌더링 — (a) 를 다시 재고 또 멈췄다 (2026-08-17)

## 결론: (a) 의 사정거리가 **46문항 기준 0/5** 다

전체 코퍼스로는 그릴 수 있어 보였다.

```

  헤더 셀 수 = 행 셀 수      6,579  (21.0%)   ← 그릴 수 있다
  열 수 다름               24,270  (77.5%)
  헤더 못 찾음                485  ( 1.5%)
```

그런데 **실제 답에 나오는 표**로 재니 0 이다.

```
46문항 중 FOUND 30건 · 그중 인용이 표인 것 5건
  전부 kind='table' (표 전체)     → 헤더/행 셀 = 1/15, 1/21, 1/43 …
  kind='table_row' 는 0건
```

★ **인용은 자족성 승격 때문에 부모 블록(표 전체)으로 올라간다.**
  행 단위(table_row)는 인용에 안 나온다. 그래서 행 단위로 그리는 규칙은
  실제 답을 하나도 못 건드린다.

  이건 전에 표 전치를 되돌릴 때 적은 결론과 같다 —
  "필요하면서 가능한 건이 0건". 자를 바꿔도 그 결론이 유지된다.

    ③ 우리문구  92%   ← 아플 것 같았던 곳
    ② 변형      46%   ← 실제로 아픈 곳

목록을 훑고 "이건 아프겠다" 는 짐작은 자가 아니다.
아픈 곳을 고르는 일에도 자가 필요하다.

### ③ **도구를 만드는 것과 쓰는 것은 다른 일이다**

오늘 오전에 '재는 자가 실제 경로와 달랐다' 를 두 번 겪고
`tools/answer_path.py` 를 만들었다. 갈래를 흉내내지 않고 route_of 에서
끌어오는 도구다.

그리고 오후에 `variant_probe` 를 만들며 **그 도구를 안 썼다.**
`S.search` 로 직접 쟀고, `시험언제` 가 틀린 것으로 잡혔다 —
그 질문은 학사일정으로 간다.

    같은 날 · 같은 사람 · 같은 병
    도구를 만들었다고 다음 도구가 그것을 쓰는 게 아니다.

★ 새 측정 도구를 만들 때 **첫 줄에서 물어야 한다**:
  "이 갈래를 정하는 코드가 이미 있나?"

## 시트에 기대는 경로는 **로컬 판정을 근거로 쓰지 않는다** (2026-08-28)

웰컴 버튼을 확인하다 `총학생회 공지` 가 로컬에서 이렇게 나왔다.

    로컬   "최근 총학 공지를 아직 못 가져왔어요. 시트를 마지막으로 읽은 지 오래됐어요."
    서버   "지금 진행 중인 총학 공지가 없어요. 새로 올라오면 여기서 바로 보여드릴게요."
           [ 총학 인스타 열기 ]

같은 0행인데 뜻이 정반대다.

    로컬 council_post 0행        = **못 긁음**       ← 우리 고장
    서버 시트 연결됨 + 0행        = **학교가 안 올림**  ← 정직한 답 + 출구

'없다' 의 갈래에서 다른 칸이다. 이번에는 **자가 실제보다 나쁘게 말했다** —
그 말을 믿었으면 웰컴 버튼에서 뺐을 것이다.

★ 시트·크롤에 기대는 경로(council · 학식 · 학사일정)는 로컬 결과를
  '고장' 의 근거로 쓰지 않는다. 서버에서 한 번 쳐 보고 판단한다.

## 첫 화면 기준 — 거르는 자만 있고 **고르는 자**가 없었다

    있던 기준   첫 화면에 되묻기가 나오면 안 된다        ← 안 될 것을 거른다
    없던 기준   첫 화면은 학생이 많이 묻는 것이어야 한다   ← 무엇을 넣을지 정한다

거르는 자만 있으면 통과한 것 중 아무거나 들어간다. 실제로 '자퇴 절차' 가
첫 화면에 있었고, 폴백 101종에서 자퇴 계열은 상위에 없었다.

## 규칙 — 주석에 **결론만** 적지 말고 **전제**를 같이 적는다 (2026-08-28)

같은 결함을 이틀에 걸쳐 앞뒷면으로 만났다.

    어제  calendar_search.rank 주석    아직 유효한데 **안 읽고** 다시 물었다
    오늘  '총학 공지는 뺀다' 주석      무효가 됐는데 **안 지웠다**

    "'총학 공지' 는 원천이 인스타라 뺐다 — 크롤이 못 닿는다"

T4 시트를 붙이면서 그 전제가 무너졌는데 결론(첫 화면에서 뺀다)만 남았다.
**근거가 사라진 뒤에도 결론은 남는다.** 그리고 결론만 읽으면 왜인지 모른다.

★ 결론 옆에 그것이 기대는 전제를 적는다. 전제가 무너지면 결론도 같이 흔들리게.

★ 그리고 이번 건은 **전제가 안 적혀서 난 게 아니다** — 적혀 있었다.
  시트 작업이 그 파일을 지나가지 않았을 뿐이다. 그래서 하나 더:

    원천을 바꾸는 커밋은 **그 원천 이름으로 전체 검색을 한 번 하고 끝낸다.**
    (이번 경우 `인스타` · `instagram`)

  전제를 적는 것은 다음 사람을 위한 것이고, 전체 검색은 **지금 나를 위한 것**이다.

## 규칙 — 틀린 자는 **어느 쪽으로든** 틀린다

지금까지 자가 틀릴 때는 늘 **우리에게 유리하게** 틀렸다.

    34건을 통과로 셌다        · 되묻기를 이어짐으로 셌다
    '시험 62%' 를 실패로 셌다  · 회복 16건을 12건으로 셌다

그래서 "자가 틀리면 자신감이 과해진다" 로 기억하고 있었다.

오늘 반대가 나왔다.

    로컬 council_post 0행 → "못 가져왔어요"(우리 고장)
    서버 시트 연결 + 0행  → "없어요"(학교가 안 올림 · 정직한 답 + 출구)

로컬을 믿었으면 **멀쩡한 버튼을 첫 화면에서 뺐을 것이다.**
자가 불리하게 틀리면 잘 되는 것을 고장으로 알고 지운다 —
숫자가 나빠지지 않으니 알아채기도 더 어렵다.

★ 자를 의심할 때 "좋게 나왔나" 만 보지 않는다. **양쪽 다 본다.**

## 규칙 — 실서버를 잴 때는 **무엇이 떠 있는지부터** 확인하고 잰다 (2026-08-28)

`65f87f8` 푸시 직후에 쟀더니 이렇게 나왔다.

    수강신청 언제야  정상
    질병휴학        「오류가 발생하였습니다」
    오늘 학식        무응답 11초        ← 10분 전에는 정상이던 발화

「서버가 죽었다」로 읽혔다. **배포 전환 중이었다.** 몇 분 뒤 전부 정상이었다.

★ 배포 직후 몇 분간 실서버는 **관측 대상이 아니다.**
  배포 중이면 재지 말고, 잰 뒤에는 커밋 해시를 같이 적는다.

아침에 세운 규칙의 짝이다.

    아침   대표가 본 화면이 **최신 배포본이 아닐 수 있다**   (배포본이 뒤처짐)
    저녁   내가 잰 화면이 **아직 배포본이 아닐 수 있다**     (배포본이 아직 없음)

둘을 한 줄로 묶으면: **잰 것이 무엇인지 모르면 잰 게 아니다.**

### 이 사건의 교훈은 「도구」가 아니라 「시점」이다

`tools/live_probe.py` 를 오늘 한 번도 안 돌린 건 사실이고 그건 따로 고칠 일이다
(배포 후 확인 절차에 넣는다). 다만 **이번 오탐의 원인은 아니다** —
live_probe 를 돌렸어도 배포 중이면 똑같이 「죽었다」고 나왔다.

★ 반성을 정확한 자리에 붙인다. 섞으면 다음에 엉뚱한 걸 고친다.

### 그리고 못 찾았을 때 「못 찾았다」고 말한 것

로컬에서 예외 0 · 규격 ok · 성능 1~41ms · config ok 까지 확인하고도
원인을 못 찾았다. 그때 **가설을 만들어 내지 않고 그대로 보고**했다.
파고들었으면 없는 원인을 만들어 코드를 고쳤을 것이다.

★ 배제한 목록은 그 자체로 결과다. 원인을 못 찾은 것과 아무것도 못 얻은 것은 다르다.
