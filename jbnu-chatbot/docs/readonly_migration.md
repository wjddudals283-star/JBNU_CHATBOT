# 답변 경로가 읽기 전용이라 마이그레이션을 못 한다

색인 확대를 시도하다 발견했다. 색인과는 **별개 문제**이고, 다음에 스키마를
바꿀 때도 똑같이 물린다. 지금 안 고쳐도 되지만 모르고 있으면 배포가 죽는다.

## 무엇이 일어나나

`page_section` 에 열을 하나 추가하고 답변 경로가 그 열을 읽게 했더니,
**열이 없는 기존 DB 에서 검색이 통째로 죽었다.**

```
sqlite3.OperationalError: no such column: is_indexed
```

`ensure_columns()` 에 `ALTER TABLE` 을 넣어 뒀는데도 그랬다. 이유는 둘이다.

1. **답변 경로가 `ensure_columns` 를 안 부른다.** 부를 이유가 없었다 —
   읽기만 하는데 스키마를 고치는 함수를 부르는 건 이상하다.
2. **부를 수 있어도 못 한다.** 콜드 스타트를 고치면서 답변 경로를
   `readonly=True` (`file:...?mode=ro`) 로 바꿨다. 읽기 전용 연결에서는
   `ALTER TABLE` 이 실패한다.

즉 **읽기 전용으로 만든 것이 마이그레이션 경로를 막았다.** 둘 다 옳은 결정이었고
따로 보면 문제가 없는데, 겹치면 스키마 변경이 배포를 깬다.

## 배포 순서가 만드는 창

Render 는 새 코드를 띄우고 헬스체크가 통과하면 트래픽을 넘긴다.
디스크의 DB 는 **그대로**다. 그 사이에 오는 요청은 새 코드 + 옛 스키마를 만난다.

```
t0  새 코드 배포          답변 경로가 새 열을 읽으려 한다
t1  첫 요청              옛 DB 에 그 열이 없다 → 검색 죽음
t2  스케줄러가 수집 시작    그때서야 쓰기 연결로 ensure_columns 가 돈다
```

t1~t2 사이가 창이다. 수집이 03:10 에만 돌면 **최대 하루**다.

## 다음에 스키마를 바꿀 때

셋 중 하나를 고르면 된다. 아직 정하지 않았다.

1. **기동 시 쓰기 연결로 한 번 마이그레이션한다.**
   워밍업이 이미 기동 시 도는 자리다 (`server._warmup`). 거기서
   쓰기 연결로 `ensure_columns()` 를 부르고 닫으면 된다.
   답변 경로는 읽기 전용 그대로 둔다.
   ★ 다만 워밍업은 "실패해도 서버는 뜬다" 는 규약이다. 마이그레이션을
     거기 두면 그 규약이 깨진다 — 실패하면 뜨면 안 되기 때문이다.

2. **읽는 쪽이 열이 없는 경우를 견딘다.**
   `PRAGMA table_info` 로 확인하고 없으면 옛 질의를 쓴다.
   조용히 옛 동작으로 도는 것이라, 그 사실이 로그에 남아야 한다.

3. **새 열을 안 쓴다.** 계산으로 대신할 수 있으면 그게 가장 싸다.
   `is_indexed` 는 사실 `is_leaf` + 페이지별 d0 개수로 질의 시점에
   계산할 수 있었다. 열을 만든 건 네 군데에 조건을 반복하기 싫어서였다.

## 관련

- 콜드 스타트 고침 (읽기 전용 연결) — `store/repo.py: connect(readonly=True)`
- 워밍업 — `skill/server.py: _warmup()`
- 실패한 색인 확대 — `skill/section_search.py` 의 `PROBE_DF_MAX` 위 주석
